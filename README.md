# Threadline — Quality Inspection Tracker

React/Vite/Tailwind frontend, Express/pg backend and PostgreSQL. Log fabric defects, filter and sort inspections, load more results by scrolling, resolve findings with a required note, and review global severity/status counts.

## Requirements

- Node.js 24 LTS (22.12+ supported) and npm
- PostgreSQL 16+

## Setup

1. Create the database (as a PostgreSQL administrator, using pgAdmin or psql):

   ```sql
   CREATE DATABASE "tracker-dev" OWNER postgres;
   ```

2. Copy [backend/.env.example](backend/.env.example) to `backend/.env` and set your database credentials:

   | Variable    | Purpose                                 |
   | ----------- | --------------------------------------- |
   | DB_HOST     | PostgreSQL host (`localhost`)           |
   | DB_PORT     | PostgreSQL port (`5432`)                |
   | DB_USERNAME | PostgreSQL user                         |
   | DB_PASSWORD | PostgreSQL password                     |
   | DB_NAME     | Database name (`tracker-dev`)           |
   | PORT        | API port (`3001`)                       |
   | CORS_ORIGIN | Frontend origin allowed to call the API |

3. Copy [frontend/.env.example](frontend/.env.example) to `frontend/.env`. It sets `VITE_API_BASE_URL=http://localhost:3001/api`.

4. Install dependencies and apply migrations from the repository root:

   ```sh
   npm ci
   npm ci --prefix backend
   npm ci --prefix frontend
   npm run db:migrate --prefix backend
   ```

5. Load dummy data for local development:

   ```sh
   npm run db:seed --prefix backend
   ```

6. Start the API and the frontend in separate terminals, then open http://localhost:5173:

   ```sh
   npm run dev --prefix backend
   npm run dev --prefix frontend
   ```

Env files are ignored by source control.

## Database

Migrations live in [backend/src/db/migrations/](backend/src/db/migrations/). The runner applies pending files in filename order, each in its own transaction, and records them in `schema_migrations`.

| Migration                           | Purpose                                                         |
| ----------------------------------- | --------------------------------------------------------------- |
| 001_create_inspections.sql          | Inspections table, constraints and filter indexes               |
| 002_inspection_uuid_and_indexes.sql | UUID primary key (`legacy_id` column), summary and sort indexes |

Indexes on `inspections`:

| Index                 | Supports                                      |
| --------------------- | --------------------------------------------- |
| (severity)            | Severity filter                               |
| (status)              | Status filter                                 |
| (severity, status)    | Summary `GROUP BY severity, status`           |
| (inspection_date, id) | Date range filter and date sort (both orders) |
| (created_at, id)      | `createdAt` sort                              |

Inspection IDs are UUIDs generated by PostgreSQL `gen_random_uuid()`.

Database commands (run from the repository root):

```sh
npm run db:migrate --prefix backend              # apply pending migrations
npm run db:status --prefix backend               # list applied/pending migrations
npm run db:new --prefix backend -- add_column    # create the next numbered migration
npm run db:seed --prefix backend                 # insert 300 dummy inspections
```

Never edit an applied migration; add a new one instead. Back up with `pg_dump` before running migrations on shared data.

The seed SQL lives in [backend/src/db/seeds/](backend/src/db/seeds/) and is not part of migrations. It inserts 300 inspections covering every defect type, severity and status, dated within the last 30 days. It skips inserting when rows with remarks starting "Dummy remark" exist.

## Architecture

- [Frontend](frontend/README.md): dashboard, inspection register, dialogs, API client and infinite-scroll feed.
- [Backend](backend/README.md): API routes, validation, services, constants and configuration.

New inspections start Open. Resolving requires a note, and resolving twice returns 409. Summary counts are global and ignore list filters.

The list API returns `data.items` and `data.pagination` (`page`, `limit`, `returned`, `total`, `hasMore`). `total` is the number of records matching the filters. The frontend loads 20 records at a time as you scroll, restarts from page 1 when filters or sorting change, and stops at the last page. The overview shows the six most recent inspections.

## Verification

```sh
npm run lint
npm run format:check
npm run build
```

`npm run format` applies Prettier formatting. The backend build checks JavaScript syntax.

## Limitations

Pagination uses `LIMIT`/`OFFSET` with a UUID tie-breaker. Records added or changed by other users while scrolling can shift pages; the UI removes duplicate rows. Authentication, editing, deleting and reopening inspections are not supported.
